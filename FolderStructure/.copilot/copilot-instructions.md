# Copilot Instructions

## 專案定位
- 本專案採用 Spec-Driven Development（SDD）方式進行需求分析、系統設計、任務拆解與程式開發。
- 所有功能應先完成需求與規格整理，再進入實作。
- 若需求、規格、流程或上下文不完整，請先提出問題，不要自行猜測。

## 專案資料夾結構
- `Docs/PRD`：放產品需求、商業需求、使用情境與需求說明文件。
- `Docs/Spec`：放系統分析、功能規格、流程設計、API 規格、資料模型等技術文件。
- `Docs/Task`：放任務拆解、待辦項目、實作清單與執行計畫。
- `Backend/src`：放後端主要程式碼。
- `Backend/shared`：放後端共用模組、基礎元件或共享程式碼。
- `Backend/tests`：放後端測試程式。
- `Frontend/src`：放前端主要程式碼。
- `.copilot/copilot-instructions.md`：放全專案共通的 Copilot 指引。
- 角色相關 prompt files、path-specific instructions 與其他客製化設定可另外放在 `.copilot/prompts/` 底下的適當位置。

## 文件優先原則
- 開始任何工作前，優先閱讀 `Docs/PRD`、`Docs/Spec`、`Docs/Task` 中與目前任務相關的文件。
- 文件閱讀順序原則上為：
  1. `Docs/PRD`
  2. `Docs/Spec`
  3. `Docs/Task`
- 若文件已明確定義需求、規格、流程、欄位、API 或待辦項目，應優先依照文件內容執行。
- 若文件與現有程式碼不一致，先指出差異、風險與建議做法，再開始修改。

## 工作方式
- 本專案採用角色分工的工作流程。
- 新需求開始時，先由 BA 與使用者互動，釐清需求、商業目標、範圍、使用者情境與限制條件，並產出 PRD。
- PRD 完成後，再由 SA 根據 PRD 進行系統分析與設計，產出 Spec。
- SA 應根據 PRD 產出以下內容：
  - 系統分析結果
  - 功能規格
  - 模組與流程設計
  - API / 資料模型 / 欄位規格
  - 任務拆解
  - 待辦項目
  - 實作清單
- 在 PRD 或 Spec 尚未完成前，不應直接進入程式實作。
- 若仍有待確認事項，應先提出問題與假設，再決定下一步。
- 若任務涉及前後端或多模組相依，應先說明相依關係與建議順序。

## 實作前的互動方式
- 在開始撰寫程式、修改文件或調整結構前，先輸出：
  1. 對需求的理解
  2. 目前依據的文件
  3. 建議的實作或處理步驟
  4. 預計修改的檔案、模組或文件
- 若存在多種可行方案，先列出方案、差異、優缺點與建議選項，再開始執行。
- 若任務範圍不明確，先縮小範圍並與使用者確認。

## 變更原則
- 優先進行小而清楚、範圍可控的修改。
- 不要修改與當前任務無關的檔案。
- 不要自行進行大規模重構，除非任務明確要求或已有文件支持。
- 不要在未經說明的情況下新增大型依賴、框架或全新架構。
- 若需要跨 `Backend`、`Frontend`、`Docs` 多個區域調整，應先明確說明修改原因與影響範圍。

## 文件產出原則
- BA、SA、Backend、Frontend 各角色的具體規則與輸出格式，可以定義在各自的 prompt files 或其他角色專用設定檔中。
- 本檔案只放全專案共通規則，不重複描述各角色的細部實作規範。
- 若任務需要產出 PRD、Spec 或 Task 文件，應依照目前流程與既有文件風格維持一致性。
- 新增文件時，內容應清楚區分需求、規格、任務與實作層次，不要混寫。

## 程式與文件品質原則
- 內容應優先追求清楚、可讀、可維護與一致性。
- 使用具描述性的命名，避免含糊不清的名稱。
- 回覆與輸出內容應具體、可執行、可驗證。
- 僅在必要時加入註解，避免撰寫無實質意義的註解。
- 若引用既有檔案、路徑、類別、方法或模組，應使用正確名稱。

## 驗證與完成標準
- 完成工作後，應整理並輸出：
  1. 本次完成內容
  2. 修改的檔案或文件
  3. 風險與假設
  4. 待確認事項
  5. 建議的後續步驟
- 若任務涉及文件更新，應說明更新的是 PRD、Spec、Task 或程式碼。
- 若任務尚未可直接實作，應明確指出目前卡在哪一層：需求、規格、任務拆解或實作。
- 若目前階段仍屬需求分析、系統設計或任務拆解，請不要假裝已完成開發實作。

## 回覆語言
- 回覆與說明以繁體中文為主，並使用台灣習慣用語。
- 技術名詞、框架名稱、檔名、路徑、類別名稱、方法名稱、欄位名稱可保留英文。
- 若輸出文件範本、任務清單或分析結果，格式應保持清楚、條列化、容易延續使用。

## 行為提醒
- 先理解，再設計，再拆解，再實作。
- 先文件，後程式。
- 先確認，後修改。
- 若不確定，先提出問題，不要猜測。
